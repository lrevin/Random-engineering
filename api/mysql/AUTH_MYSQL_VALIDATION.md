# MySQL 인증·로그인 유지 전환

> 이식 전 검증에 더해 C:/Coding/Random-engineering에서도 인증 14개·DB 8개·회귀 6개 테스트를 재실행하여 통과했다. 실제 앱은 아직 Supabase이며, 전환 후보는 app-integration에 별도로 보관한다. 현재 적용 상태와 선택 방법은 [MySQL 전환 안내](README.md)를 따른다.

검증일: 2026-11-07. 실제 MySQL 8.0.46의 기존 ppobgong DB를 사용했다. 테이블 변경은 없으며 기존 19개 테이블 중 계정·로그인 수단·세션·회전 토큰·사용자 동기화 상태를 사용한다.

## 구현 범위

- POST /auth/signup, /auth/login, /auth/refresh, /auth/logout, GET /auth/me.
- BCrypt 비용 12, HS256 JWT 15분, 30일 절대 만료 세션, SHA-256 Refresh Token 저장·회전.
- 현재 계정 상태·auth_version 확인, 소비 토큰 재사용 시 세션 폐기.
- IP 요청 제한, 요청 형식·크기 검사, 비밀 값 미출력, 인증 응답 캐시 금지.
- 앱에서 API URL을 지정하면 Supabase 인증을 대신한다. 로그인 정보 복원·갱신·로그아웃과 SecureStore(모바일)/sessionStorage(웹) 연결.
- 프로필·기록 API가 전환되기 전이므로 MySQL 인증 계정의 데이터는 기기에서 계정별로 보관한다. Supabase와 계정을 혼합하거나 다른 계정의 데이터를 전송하지 않는다.

## 검증 결과

`npm run auth:test`: 14개 통과(상위 1개·세부 13개).

1. 이메일 정규화·가입, BCrypt 비용·비밀번호 해시, 토큰 해시와 동기화 상태 초기화.
2. 중복 가입·잘못된 입력·비밀번호 72바이트 상한.
3. 올바른/잘못된 로그인, 로그인별 세션 분리.
4. 토큰 회전·절대 만료 유지·소비 토큰 재사용 시 해당 세션 폐기.
5. 같은 Refresh Token 동시 요청의 한 번만 성공 및 재사용 차단.
6. 로그아웃·반복 로그아웃·갱신 차단·기존 Access Token 만료 유지 정책.
7. JWT 만료·서명·audience, auth_version 변경, 탈퇴 예약 계정 접근 거절.
8. 세션 만료 시 갱신 거절.
9. 잘못된 JSON·과대 본문·잘못된 메서드·CORS.
10. IP 요청 제한.
11. 실제 앱 인증 클라이언트의 가입·저장·재시작 복원·동시 갱신 단일화.
12. 만료 Access Token의 갱신 복원·거절된 Refresh Token의 로컬 정리.
13. 네트워크 오류 시 보존·갱신 중 로그아웃 후 세션 부활 방지.

기존 JSON/API 회귀 테스트 6개와 MySQL 통합 테스트 8개도 통과했다. 앱 타입 검사·코드 검사·웹 빌드를 수행했다. 실제 MySQL에 남은 테스트 계정은 종료 시 삭제하며 기본 문제는 유지한다.

## 제한

이메일 인증 메일·비밀번호 재설정·소셜 로그인·기존 Supabase 계정 이전·회원 탈퇴·프로필 및 학습 기록 서버 동기화는 미전환이다. 새로운 가입의 email_verified_at은 NULL이다. 이미 발급한 Access Token의 로그아웃 즉시 무효화는 명세대로 보장하지 않는다.

클라이언트 테스트는 앱에서 사용하는 실제 인증 모듈을 실행하되 저장소는 테스트 어댑터를 주입했다. React 화면 조작·실제 기기 SecureStore·앱 종료 및 재실행의 실기기 검증은 아직 수행하지 않았다. 웹 토큰은 탭 단위 저장이며 탭을 닫은 뒤 로그인 유지까지 보장하지 않는다.
