# 뽑공 MySQL 기반 전환 정리

최종 갱신: 2026-11-14

이 문서는 **MySQL 기반 전환 및 Supabase 잔여 코드·의존성 제거의 현재 상태**를 계속 갱신하는 기준 문서다. 작업 당시의 고정 기록이 아니다.

최신 develop 통합, 기능별 완료·일부 구현·미구현 상태와 앞으로 할 일은 [개발 진행 현황](DEVELOPMENT_PROGRESS.md)에서 관리한다. 두 문서의 상세 내용을 중복 작성하지 않고, 공통 DB 구조·검증 결과·배포 상태는 함께 맞춘다.

2026-11-14 기준 로컬 개발 DB와 운영 RDS는 V5까지 적용·검증됐다. 최신 API·검사·앱 소스를 EC2에 반영하고 Supabase 잔여 실행 코드·의존성을 정리했다. HTTPS 운영 검사와 릴리스 APK 재빌드·서명 검증을 완료했다. 휴대폰·에뮬레이터 간 친구·배틀 정상 동작은 사용자 확인이며, 모든 기능·장애 상황의 기기 검증은 별도다.

## 1. 작업 목표

Supabase 기반 앱을 자체 API 서버와 MySQL 기반으로 전환하고, 팀원이 APK를 설치하면 별도의 서버 설정 없이 사용할 수 있도록 구성한다.

GitHub에는 MySQL 인증·프로필·학습 기록·문제 조회 API가 이미 포함되어 있었다. 현재 로컬 구현은 해당 기능을 실제 앱에 연결하고, 인증 제공자 선택과 Supabase 실행 의존성을 제거한 상태다.

화면 디자인, 친구·배틀, 광고·상점 등 별도로 추가된 기능은 MySQL 전환과 구분한다. MySQL 인증이 연결됐다는 이유만으로 모든 부가 기능의 서버 전환이 완료된 것은 아니다.

## 2. 앱·API·DB 연결 구조

기존에는 앱이 Supabase SDK로 인증과 데이터 조회·저장을 요청했다. 현재는 자체 API 서버를 거친다.

```text
앱
 └─ https://ppobgong.o-r.kr
     └─ Nginx
         └─ 자체 API 서버:8788
             └─ MySQL
```

- 앱은 DB에 직접 접속하지 않는다.
- API 서버가 인증·소유권·입력값을 검사한다.
- DB 비밀번호와 JWT 비밀 키는 서버에서 관리한다.
- AI 문제 생성은 별도 퀴즈 AI 서버 경로를 두되 실제 서비스 연결은 보류한다.
- 친구·랜덤 매칭·배틀은 같은 자체 API와 MySQL 인증·저장을 사용하며 EC2에 반영 완료했다.

## 3. 인증·로그인 유지

| 항목 | 기존 방식 | 현재 방식 |
|---|---|---|
| 가입·로그인 | Supabase Auth SDK | 자체 `/auth/*` API |
| 사용자·인증 정보 | Supabase 관리 계정 | `users`, `auth_identities` |
| 로그인 세션 | SDK 관리 | `auth_sessions`, `refresh_tokens` |
| 비밀번호 | Supabase 처리 | 서버의 BCrypt 처리 |
| Access Token | SDK 관리 | 자체 JWT 발급·검증 |
| 로그인 유지 | SDK 자동 갱신 | 앱 인증 클라이언트와 Refresh Token 회전 |
| 모바일 토큰 보관 | 기존 SDK 저장 방식 | SecureStore |
| 웹 토큰 보관 | 기존 SDK 저장 방식 | 탭 단위 sessionStorage |

현재 앱은 MySQL API만 사용한다.

- `EXPO_PUBLIC_AUTH_PROVIDER`에 따른 선택 구조를 제거했다.
- `EXPO_PUBLIC_API_URL`은 필수다.
- API 연결 실패 시 다른 인증 서비스로 전환하지 않는다.
- 네트워크 오류와 인증 만료를 구분한다.
- 기존 Supabase 계정·기록의 자동 이전은 지원하지 않는다.

인증 관련 역할은 다음처럼 구분된다.

| 파일 | 역할 |
|---|---|
| `auth.ts` | MySQL 인증 클라이언트 생성과 사용자용 오류 안내 |
| `auth-client.ts` | 가입·로그인·토큰 갱신·프로필·기록 API 요청 |
| `auth-storage.native.ts` | 모바일 로그인 정보 저장 |
| `auth-storage.ts` | 웹 로그인 정보 저장 |
| 서버의 `auth.mjs`, `auth-http.mjs` | 인증 처리와 HTTP 경로 |

## 4. 프로필·회원 탈퇴

프로필은 자체 API로 조회·저장하고 기기에는 캐시한다.

| 기능 | API |
|---|---|
| 프로필 조회 | `GET /me/profile` |
| 프로필 생성·수정 | `PUT /me/profile` |
| 탈퇴 신청 | `DELETE /me` |
| 탈퇴 취소 | `POST /auth/cancel-deletion` |

탈퇴 신청 시 즉시 이용을 차단하고 로그인 세션을 폐기한다. 7일 이내에는 비밀번호 확인으로 취소할 수 있으며, 유예기간이 지난 계정은 정리 작업으로 삭제한다.

화면과 개인정보 안내는 현재 인증·저장 방식 및 탈퇴 정책에 맞췄다. 만료 계정 정리 명령의 운영 스케줄 등록 여부는 별도 확인 대상이다.

## 5. 학습 기록·답안·XP

앱의 결과 요약을 DB에 직접 저장하던 방식에서, 자체 API가 기록과 답안을 검증·저장하는 방식으로 변경했다.

주요 처리:

- 완료한 풀이의 문제 스냅샷·사용자 답안 저장.
- 동일 기록 재전송 시 중복 저장·XP 중복 지급 방지.
- 서버에서 정답 수·오답·XP 계산.
- 기록 삭제 시 XP 지급 취소 및 삭제 표식 저장.
- 메모 수정 시 변경 순번을 이용한 충돌 감지.
- 같은 식별자로 다른 내용이 들어오면 무조건 덮어쓰지 않음.

| 테이블 | 역할 |
|---|---|
| `quiz_attempts` | 풀이 시도 |
| `quiz_attempt_items` | 문항별 문제 스냅샷·사용자 답안 |
| `study_records` | 완료한 학습 결과 |
| `user_sync_states` | 사용자별 동기화 순번 |
| `study_record_tombstones` | 기록 삭제 동기화 |
| `xp_ledger` | XP 지급·취소 원장 |

실제 구현은 초기 설계 메모와 차이가 있다. 사용자·기록 등에 UUID 문자열을 사용하고, 문항별 기록은 `study_record_detail` 대신 `quiz_attempt_items`로 관리한다.

기본 문제는 서버가 보존한 원본의 본문·보기·정답·해설과 대조하며, 보기 순서 변경과 중복 문항도 검사한다. 일치한 원본 문제 ID를 문항별 기록에 저장한다. 전체 문항이 원본과 일치하면 `server_verified`, AI·기기 생성 문제가 섞이면 `client_reported`로 구분한다.

스피드 퀴즈는 서버가 발급한 문제·답안을 별도 `speed_runs`, `speed_answers`에 저장한다. 확정 XP는 회원 전체 XP에 합산하지만 일반 7문항 학습 기록이나 분야 랭크에는 섞지 않는다. 세부 보상·시간 정책은 개발 진행 현황에서 관리한다.

기본 문제 원본 대조만으로 실제 학습 행동·시간을 증명하는 것은 아니다. `client_reported` 결과를 포함한 부정행위 검증의 남은 범위를 구현 완료로 표시하지 않는다.

## 6. 로컬 저장·오프라인 동기화

다음 기능을 유지한다.

- 진행 중 학습 상태와 완료 기록의 기기 저장.
- 전송 실패 시 동일 기록 ID로 재시도.
- 서버 성공 확인 후 전송 완료 처리.
- 계정별 기기 보관본·기록 분리.
- 동일 계정 재로그인 시 데이터 복원.
- 계정 변경 중 도착한 이전 응답의 반영 방지.
- 메모 충돌 시 로컬 초안과 서버 내용 선택.
- 서버에서 삭제한 기록이 다른 기기에서 복원되는 문제 방지.

기존 `pg.mysql.*` 저장 키를 유지했다. 코드 정리를 위해 기기에 보관된 MySQL 계정 데이터와 캐시를 초기화하지 않는다.

## 7. 기본 문제·AI 문제

### 기본 문제

현재 기본 문제 은행 전체를 앱에 포함한다. 앱의 기본 문제 조회는 내장 데이터를 즉시 사용하므로 별도 다운로드나 인터넷이 필요하지 않다.

- 현재 원본: JSON 21개·220개 주제·5,520문제·2,232,426바이트(약 2.13MiB). 전체 주제 목록은 1,054개이며 모든 주제에 30문제가 완성됐다는 의미는 아니다.
- 분야별 다운로드·업데이트·삭제 화면, 로컬 묶음 모듈 및 GET /quiz-downloads/:domainId는 앱·EC2에서 제거했다. 운영 경로는 404를 반환한다.
- 동일한 JSON 원본을 MySQL에도 적재해 서버 배틀 출제·일반 풀이 원본 대조에 사용한다. GET /quiz-bank/:topicId는 유지한다.
- 부분 내장 빌드에서만 사용하는 주제별 API·ETag·7일 캐시·통신 실패 대체 경로는 남아 있다. 현재 전체 내장 빌드에서는 이 경로보다 내장 문제가 우선이다.
- 저장된 문제가 부족하면 기존 기기 생성 대체 문제로 보충한다. 나머지 일반 오프라인 저장·동기화·보상 정책의 추가 변경은 후속 검토다.
- GET /catalog의 DB 목록·버전·활성 상태 및 영구 캐시는 유지한다. 문제 다운로드 기능 제거와 구분한다. 영어 문서명·힌트·아이콘은 내장 자료로 보완한다.

### AI 문제

별도 AI 서버 요청, 받은 문제의 기기 캐시, 기본 문제·대체 문제로 보충하는 흐름을 유지한다. AI 실서비스 연결은 사용자 요청으로 보류 중이다. EC2의 AI 주제 경로도 api/shared/data/topics.json으로 통일하고 잠금 파일 기준 패키지 설치·모의 검사를 완료했으며, 상시 AI 서비스는 시작하지 않았다.

Supabase 서버 함수를 호출하던 대체 경로는 제거했다. AI 서버의 JSON pool을 MySQL 문제 은행으로 직접 수신·적재하는 기능은 별도로 연결해야 한다.

## 8. DB 구조·접근 제어·마이그레이션

### DB 구성

| 영역 | 주요 테이블 |
|---|---|
| 회원·인증 | `users`, `auth_identities`, `auth_sessions`, `refresh_tokens` |
| 분류·프로필 | `domains`, `categories`, `topics`, `profiles` |
| 문제·파일 이력 | `question_files`, `question_file_topics`, `questions`, `question_details`, `question_file_items` |
| 풀이·기록·XP | `quiz_attempts`, `quiz_attempt_items`, `study_records`, `user_sync_states`, `study_record_tombstones`, `xp_ledger` |
| 재화 | `wallets`, `wallet_transactions`, `wallet_operations` |
| 자격증 | `certificates`, `certificate_subjects`, `certificate_subject_items` |
| 친구 | `social_members`, `social_friendships` |
| 스피드 퀴즈 | `speed_runs`, `speed_answers` |
| 배틀·매칭 | `battles`, `match_entries` |

현재 로컬 V1~V5 마이그레이션 기준 업무 테이블은 31개다. Flyway 이력 테이블은 이 수에 포함하지 않는다. 테이블 존재와 해당 기능의 API·앱 연결 완료는 구분한다.

| 버전 | 반영 범위 |
|---|---|
| V1 | 회원·문제·기록·재화 등 기본 구조 |
| V2 | 자격증 관련 3개 테이블 |
| V3 | 친구 코드·신청·관계 2개 테이블 |
| V4 | 스피드 출제·답안·확정 XP 2개 테이블 |
| V5 | 배틀·대기열 2개 테이블, 공통 기록 유형·5~10문항·부호 있는 배틀 XP |

로컬 개발 DB는 백업 후 V2→V5를 적용했고 RDS와 V1~V5 이력·체크섬이 일치한다. 양쪽 모두 업무 테이블 31개, Flyway 이력 포함 32개다. 이번 환경 정리에서는 RDS에 추가 변경하지 않았다.

기존 적용 파일을 덮어쓰지 않고 새 버전으로 추가한다. 최신 코드가 기대하는 스키마와 운영 DB 이력의 일치는 배포 전에 별도로 확인해야 한다.

퀘스트 날짜의 공통 설정은 `app/src/lib/quest-time.ts`의 `QUEST_TIME_ZONE = "Asia/Seoul"`이다. 앱과 서버 생성 모듈이 같은 날짜·기간 함수를 사용하며 기기/프로세스 기본 시간대에 의존하지 않는다. 운영 출석 지급·중복 차단을 확인했고 DB 구조·기존 지급 키 형식은 유지한다.

일반 API 요청 전 `/auth/me`를 매번 호출하지 않고 대상 API가 토큰·계정·소유권을 직접 검증한다. 앱 복원·명시적 로그인 확인과 만료/401 토큰 갱신은 유지한다. `/auth/me` 요청 한도는 검증된 회원별로 분리해 Nginx 뒤 여러 기기가 같은 한도를 소진하지 않도록 한다.

Supabase RLS 대신 자체 API에서 인증 토큰과 소유권을 검사한다. DB의 FK·UNIQUE·CHECK와 서버 트랜잭션을 함께 사용한다.

### 배틀의 공통 기록·정산

- `battles`는 양측의 공통 문제·시간·답안·승패를, `match_entries`는 회원별 대기·권 예약·취소/만료를 보존한다. 활성 대기/매칭은 회원당 하나만 허용한다.
- 완료한 문제는 별도 배틀 상세 테이블 없이 기존 `quiz_attempts`·`quiz_attempt_items`·`study_records`를 재사용한다. `study_type`은 일반/배틀, `battle_id`는 승부 연결, `rank_score`는 본 문제 정답 수다.
- 일반 기본값은 7문항이며 DB·API 허용 범위는 5~10문항이다. 배틀은 본 문제 5개 + 실제 출제된 연장전 최대 5개다. 문항 스냅샷에 본 문제/연장전 표시를 보존한다.
- `rp`와 `xp_ledger.source_type`으로 배틀의 회원 XP 증감(-100~100)을 기록한다. 일반 학습 XP는 기존 0~1,000을 유지하며 배틀에 일반 학습 XP를 중복 지급하지 않는다.
- 양측 기록·답안·XP·동기화 순번·대기 종료를 한 트랜잭션으로 확정한다. 배틀 기록의 개별 삭제는 차단한다. 일반 퀘스트와 반복 학습 XP 계산에 배틀을 넣지 않는다.
- 학습 스킵은 기존 `battles.state_json`에 회원별 동의를 보존하므로 V6나 추가 테이블은 필요하지 않다. 양쪽 합의 시 서버가 같은 퀴즈 시작 시각·5분 종료 시각을 확정하며 실제 학습 시간만 공통 기록에 저장한다.
- 진행 상태는 DB에 남기고 서버가 5초마다 만료·종료를 처리한다. 재접속은 남은 시간 안에서 복원한다. 무효 배틀은 권 반환·XP 미반영하며 완료 학습 기록을 만들지 않는다.
- 현재는 DB 단위 매칭/정산 잠금으로 동시 처리를 보호한다. 큰 동시 접속 규모의 부하 검증과 잠금 범위 최적화는 아직 수행하지 않았다.

### 자격증 관련 테이블

자격증 데이터는 다음 관계를 가진다.

```text
자격증
 └─ 시험 과목
     └─ 학습 대상 세부분야 또는 개별 주제
```

| 테이블 | 저장하는 내용 |
|---|---|
| `certificates` | 자격증 이름·시행기관·설명·표시 순서·활성 상태 |
| `certificate_subjects` | 자격증에 포함되는 시험 과목과 순서 |
| `certificate_subject_items` | 과목에 연결된 세부분야·개별 주제와 순서 |

예를 들어 정보처리기사의 특정 과목에서 자료구조 세부분야 전체 또는 일부 주제를 학습 대상으로 연결할 수 있다. 기존 분야·주제 데이터를 복제하지 않고 참조하는 방식이다.

현재 초기 데이터는 자격증 10개, 시험 과목 42개, 학습 항목 연결 538건이다.

3개로 나누면 다음을 관리하기 쉽다.

- 자격증별 과목 구성과 표시 순서.
- 여러 자격증에서 같은 세부분야·주제 재사용.
- 존재하지 않는 세부분야·주제 연결 방지.
- 과목별 연결 항목의 중복과 순서 검사.
- 자격증·과목·연결 정보의 독립적인 관리.

### 자체 서버 저장·검증 연결

친구는 `/social/*`에서 로그인 토큰·활성 회원·소유권을 검사한다. 서버가 8자리 친구 코드를 발급하고 관계를 저장한다. `x-pg-uid/name/level/xp`를 회원 신원·레벨의 근거로 사용하지 않는다.

| 저장 영역 | 역할 |
|---|---|
| `wallets` | 회원의 현재 톱니바퀴 잔액 |
| `wallet_transactions` | 지급·차감 원장과 중복 지급 방지 |
| `wallet_operations` | 요청 해시·영수증·보호권/배틀권/복구 날짜 등의 확정 상태 |
| `speed_runs`, `speed_answers` | 서버 출제 스냅샷·마감·답안·채점·확정 XP |

재화는 `GET /me/wallet`, `POST /me/wallet/operations`로 연결한다. 계정별 대기 UUID를 재사용하고 회원·지갑 잠금 안에서 가격·보상·한도를 판단한다. 잔액·원장·영수증·혜택 상태는 한 트랜잭션으로 저장한다. 동일 요청의 다른 내용은 충돌로 거부하며, 앱은 성공 후에만 혜택을 반영하고 오래된 응답을 작업 순번으로 거른다.

현재 첫 지급은 지갑이 없는 회원에게 30개 한 번, 보호권은 30개/최대 2개, 구매 배틀권은 50개/최대 5개, 무료 배틀권은 한국 시각 매월 2개다. 연속 기록 복구는 날짜당 30개, 정해진 학습 시간 연장은 10개이며 타이머는 기기에 남는다. 일반 퀘스트 조건·금액은 서버 규칙을 사용한다. 규칙 수정 시 `node scripts/export-economy-policy.mjs`로 서버 계산 모듈을 다시 생성한다. 기존 기기의 재화·프리미엄을 그대로 서버 값으로 이관하지 않는다.

스피드는 `/me/speed/stats`, `/me/speed/runs`, `/me/speed/runs/:id/answers`, `/me/speed/runs/:id/finish`를 사용한다. 출제·채점·지급 정책 및 미완료 상품은 개발 진행 현황에서 관리한다.

## 9. 앱 코드·의존성·공용 자료 관리

### 앱 상태와 화면

`app-state.tsx`는 MySQL 로그인·프로필·학습 기록·서버 재화·스피드 XP와 계정별 로컬 상태를 관리한다. 이전 인증 서비스의 세션·통신·행 변환 코드는 제거했다.

기록 목록·상세·설정 화면은 MySQL 동작을 사용한다. 기록 동기화, 메모 편집·충돌 선택, 7일 유예 탈퇴 안내는 유지한다.

### 인증·퀴즈 모듈

`auth.ts`는 MySQL 인증과 오류 안내를 담당한다. 제공자 선택 상수와 이전 오류 처리 파일 의존성을 제거했다.

`quiz.ts`는 내장 기본 문제, 기본 문제 API, 별도 AI 서버 호출 경로, 기기 캐시와 대체·스피드 연습 출제를 담당한다. AI 실서비스 연결은 보류 상태다. Supabase 문제 조회·서버 함수 호출은 제거했다.

사용 기능을 옮긴 뒤 `supabase.ts`를 삭제했다.

### 패키지·환경설정

- Supabase SDK와 전용 하위 패키지 등 8개 패키지 제거.
- 패키지 목록과 잠금 파일 갱신.
- 제공자 선택과 Supabase 공개 환경변수 제거.
- 자체 API 주소 중심으로 실행 예시 정리.
- 개인정보·실행 안내를 실제 운영 구조에 맞게 수정.

### 공용 자료와 생성 도구

공용 주제·문제 문장·출제 지침 JSON은 `api/shared/data/`에서 관리한다.

MySQL 적재 도구, AI 서버, 생성 스크립트와 CI가 이 위치를 참조한다. 문제 문장 목록은 현재 5,520문제 원본에서 생성한다.

이전 Supabase 배포 코드와 실제 앱에 병합된 중복 전환 후보 앱은 제거했다. EC2에 남아 있던 api/supabase, api/mysql/app-integration/app, app/src/lib/supabase.ts도 제거했다. 앱 패키지 명세·잠금 파일과 주 API 설치 트리에 Supabase 의존성이 없는 것을 확인했다. 전환 이력을 설명하는 문서·부정 입력 검사에 남은 문자열은 실행 의존성이 아니다. 변경 전 자료는 별도 백업으로 보관했다. 테스트는 루트 `app/`의 실제 코드를 대상으로 한다.

## 10. 도메인·EC2 운영

- `ppobgong.o-r.kr`을 EC2 공인 IP에 연결.
- Nginx에서 HTTPS 요청을 내부 API 8788번으로 전달.
- 공용 목록·문제 조회는 연결 풀(최대 10개·유휴 60초 정리)을 사용해 종료된 DB 연결을 교체한다. 2026-11-14 유휴 종료 재현·운영 HTTPS 200/304·재연결 문제 조회 검사 완료. 인증·기록 등 기존 트랜잭션 연결 방식은 유지하며 모든 DB 연결을 합친 상한이 10개라는 뜻은 아니다. 연결 풀 수정에 새 마이그레이션은 없다.
- HTTPS 인증서 발급과 자동 갱신 검사.
- `ppobgong-api.service`로 API 실행 관리.
- SSH 종료 후 실행 유지, 프로세스 자동 재시작, 부팅 시 자동 시작.

서비스 설정은 EC2에 직접 생성했다. 2026-11-13 최신 API 배포·서비스 재시작과 운영 RDS V2→V5 적용을 완료했다. Flyway 이력·체크섬과 기존 회원·학습 기록 보존을 확인했다.

공개 HTTPS로 가입·로그인·프로필·친구·두 회원 매칭·배틀권 차감·포기 정산·공통 기록 응답을 확인하고 임시 계정은 정리했다. API와 DB의 적용 전 백업은 EC2 `/home/ubuntu/backups/ppobgong/20261113T054808Z/`에 소유자 전용 권한으로 보관한다. 실제 두 기기의 전체 배틀 조작 검증과는 구분한다.

운영 반영은 GitHub를 거치지 않고 SCP 파일/압축 묶음 전송 후 SSH로 백업·반영·검사·재시작했다. 운영 배포 당시에는 커밋·push를 거치지 않았다. 이후 현재 변경을 feature/mysql-backend-integration 브랜치의 공유 커밋·push 대상으로 정리했으며, 원격 develop의 추가 병합은 하지 않았다.

2026-11-14 재비교에서 API·앱 소스·검사·패키지 명세 145개가 줄바꿈 차이를 제외하고 일치했다. 문서·Git 이력·환경별 비밀 설정·설치 패키지 폴더·빌드 결과물·실제 DB 데이터는 비교 대상이 아니다. Node는 로컬 24.22.1/EC2 22.23.5, MySQL은 로컬 8.0.46/RDS 8.4.11로 유지한다.

## 11. 기능 통합 검증 결과

실제 로컬 MySQL 8.0.46과 Flyway OSS 13.12.1을 사용해 임시 DB에서 통합 검사를 실행했다.

**현재 공유 통합 검사 124개가 모두 통과했다(실패·건너뜀 0개).** 이 수는 전환 기능뿐 아니라 후속 친구·재화·목록·스피드 검사도 포함한 전체 결과다. 전체 검사의 최신 범위는 개발 진행 현황에도 기록한다.

| 검증 영역 | 확인한 내용 |
|---|---|
| 마이그레이션 | 신규 설치, V1 baseline 후 V5까지 적용, 반복 적용, 이력 검증 |
| DB 보호 | 데이터가 있는 DB의 빈 DB 설치 요청 거부, 기존 구조 보존 |
| 회원 인증 | 가입·로그인·비밀번호 검증·JWT·토큰 회전·재사용 차단 |
| 로그인 유지 | 저장된 로그인 복원, 동시 갱신, 네트워크 오류 처리 |
| 프로필·탈퇴 | 저장·수정·소유권·유예 탈퇴·취소·만료 계정 정리 |
| 학습 기록 | 답안·스냅샷·오답·XP·중복 전송·삭제·지급 취소 |
| 동기화 | 메모 충돌·변경 순번·삭제 전파·계정 전환 중 응답 처리 |
| 기본 문제 | 원본 5,520문제 대조·반복 적재·실패 롤백·HTTP 조회 |
| 자격증 | 10개 자격증·42개 과목·538개 연결의 순서와 내용 |
| 자격증 무결성 | FK·중복·순서·반복 및 동시 적재·실패 롤백 |
| 앱 연결 | 실제 인증 클라이언트·기록 동기화·AppProvider 콜백 |
| 후속 기능 회귀 | 친구 인증·재화 중복 차단·목록·서버 스피드 채점/XP·시험 기록 격리 |

최종 앱 타입·린트 검사(경고 0개) 및 Android/Hermes 번들 생성도 통과했다. AI 서버 연습 모드 검사는 이전 전환 작업에서 통과했으며 실제 외부 AI 연결을 확인한 것은 아니다.

로컬 통합 검사의 임시 DB는 해당 실행에서 만든 것만 삭제했다. 이후 운영 배포에서는 백업 후 RDS에 V3~V5를 적용했으며, HTTPS 검사에서 만든 임시 계정 2개와 해당 데이터만 정리했다. 기존 회원·학습 기록은 보존했다.

추가로 앱 자동 검사 27개(통합 검사와 일부 중복), EC2 API·마이그레이션 회귀 9개 및 AI 모의 검사를 통과했다. 하단 UI 수정 후 타입·린트·release 빌드·전용 서명을 확인하고 에뮬레이터에 업데이트했다. 휴대폰·에뮬레이터 간 친구·배틀 동작은 사용자 확인이다. 외부 AI 실서비스·결제·모든 기기/장애 상황·대규모 부하까지 검증했다는 뜻은 아니다.
